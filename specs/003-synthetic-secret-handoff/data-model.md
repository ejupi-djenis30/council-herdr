# Broker data model

All authoritative records reside in a broker-owned local NTFS directory. Use a fresh versioned pilot database with SQLite WAL/FULL and a restrictive ACL covering the directory, database, WAL, shared memory, temp, service state and backup paths. The application verifies the installed manifest, physical project identity and store ownership before serving authority. Existing work items, runs, Team identities, proposals and ballots are read for verification only through the trusted launch contract. No migration or write to those records. A legacy, unprovisioned, corrupt or unavailable store produces an unavailable status. Workspaces that existed before the pilot have no approvals to migrate.

| Record | Key and minimum fields | Rules |
| --- | --- | --- |
| Protected configuration | Schema, broker/supervisor/operator/fake pins, project physical identity, role, adapter, fixed route, allowed principals | Installed from approved artifacts, supplied by the administrator. Reads by ordinary projection expose catalog IDs/labels only. |
| Enrollment | Project/run, role, participant principal, generation, broker epoch, UTC run deadline, start/end event IDs | Live OS handle, token proof and guard are process-local. Durable rows are history after restart. No auth material is stored. |
| Request | Random reference, version and revision, recognized tuple, initiating peer ID, request expiry, idempotency key indexed by verified initiator | Immutable business terms. Projection is scoped. Strictly validated fixed labels only. |
| Decision and grant | Unique request/revision, approver, authenticated session lease ID, decision, approval UTC and original effective expiry, one-use state | Direction A also commits the broker-private immutable entry/version binding with the decision. Durable event ordering supplies the result of races. Prompt capabilities and monotonic deadlines are memory-only. |
| Effect and receipt | Unique request/revision effect ID, claim/start stamps, private A entry/version reservation or render lease, destination ID, independent receipt ID/type, resolution source and safe failure category | Monotone state. No Start means no effect; Start without positive evidence means uncertain. Late revocation is represented separately from effect outcome. |
| A entry and version | Broker-generated internal entry ID, immutable version, fixed native label, active-version pointer and DPAPI ciphertext | Include store schema, A entry kind, ID and version in the DPAPI-authenticated envelope with the value. Validate the decoded fields against the exact bound row on Claim and Start. Never replace bytes in place or reuse an ID/version pair. Activate a replacement and retire the old version under the same writer as Claim and Start. Preserve historical binding metadata without a live value once that version is retired and unneeded. |
| B encrypted output | Broker-generated internal slot ID and DPAPI ciphertext, request binding, expiry | Never named by a caller or projected. Expire or delete staging after terminal B outcome, invalidation or restart. DB/WAL may retain only ciphertext and metadata. |
| Audit event | Monotone sequence, request/revision/effect IDs, normalized event and state, permitted actor/principal ID, UTC time, typed reason | Same transaction as transition. No free text, credential fingerprint, payload, OS handle, addresses, environment, raw SID token, raw error or stack. Preserve linkage and ordered safety evidence. |

Allow access only through bounded authenticated local messages or the read-only projection. Diagnostics and CI receive per-case counters and checks with synthetic random references. Fixture reset is an explicit administrative operation on a dedicated provisioned fixture. The history of pending decisions and completed or uncertain attempts survives ordinary UI/broker restarts. Restart invalidates the preexisting pending requests and unused approvals. Reset ends the fixture and its retained history. Provisioning may define a bounded synthetic retention period, but cannot discard unresolved state while the fixture remains active. Staged ciphertext is separate from metadata. If required encrypted storage is locked, denied, tampered, or profile resolution fails, deny access without a machine-scope or plaintext fallback.

Secret buffers stay in authorized native memory briefly and are wiped on controlled paths. The fixture uses no secret-bearing temp/display files or clipboard. Provision private directories and a host configuration without secret-bearing core dumps/crash reporting, hibernation or unprotected paging for these runs. Verify crash artifacts and the host configuration. Never collect process dumps to prove a leak gate.
