# Threat model

## Protected assets and trusted host

Protect synthetic cleartext, authentic consent, live enrollment, one-use rights, immutable recipient and route, durable effect/receipt continuity and the operator’s ability to distinguish a genuine prompt. Approvers must review verified identity and actual purpose. Use an isolated, administrator-provisioned ARM64 Windows host and local console, dedicated broker, launch supervisor, participant and operator principals, trusted OS and verified native binaries. The participant account and the Workspace/Core profile are ordinary, disposable contexts. The operator uses a dedicated local account and desktop without untrusted applications. The trusted launch supervisor and broker do not take commands from a general-purpose agent shell. A trusted fake and controlled fixture verifier are provisioned with the broker.

An attacker can run code as another process under the participant's own Windows user; control a normal agent/mod or terminal; change its workspace files, argv, local environment and request parameters; copy references and spoof UI on the participant desktop; connect to permissive local endpoints; race operations; alter a participant's clock projection; or break a client transport or process at any stage. Test an additional local user and a remote peer. Ordinary same-account attackers are part of the participant-side threat model. The trusted administrator, operator, Windows kernel, broker and fixed adapter/fake form the trusted base. Admin/debugger access, takeover of the dedicated operator profile, physical observers and deliberate operator transcription are outside this synthetic pilot. Evidence only supports the exercised host, setup and paths.

| Threat | Mitigation and observable check |
| --- | --- |
| Agent impersonation, process/PID reuse, role aliasing or tampering with writable run JSON | Trusted run publication, broker-owned generation record, held process handle, creation time and OS-authenticated per-connection peer; restrictive process and thread rights. Rebind only via the supervisor, then require new consent. C07/C09. |
| Spoofed prompt or consent, injected mouse/keyboard, inspection of reveal | Independent Windows sign-in and isolated dedicated operator session/desktop, verified installed native image and broker-authenticated UI peer. Native protected paint surface and short lifetime. Test capture and injection from the participant account and account/session switches. C01/C10. |
| Copied ID, broad OS identity or forged local broker/adapter listener | References never authorize. Apply explicit peer ACLs, verify Windows peer process handles and installation pin before exchanging authority or canary. First-instance checks, validated local-only endpoints and fail-closed collision handling. C01/C07/C09. |
| Confused deputy, changed project, substituted destination or redirected response | Store an immutable exact tuple and fixed adapter; reject changed terms and all redirects. Fake uses a broker-private authenticated channel and cannot select onward routes. C07/C09. |
| Duplicate, stale grant, revoked attempt, interrupted durable write | Serialize durable mutations, validate context at both fences, one operation ID and a unique one-use constraint. Reconcile only by read-only positive evidence. C03–C08. |
| Cleartext through OS state, tool outputs, files, logs or error reflection | Segregated identity and store, DPAPI current user, fixed schema, no echo, no agent canary, memory/renderer controls, safe test detector. Explicit capture and crash-path controls in C10. |
| Availability loss or malformed/unknown protocol input | Bounded frames, typed failure and timeout, strict schemas and limits. Disable only vault actions. Persist any uncertainty and continue ordinary Council work. C01/C08–C10. |

Protected process here means a process with explicitly provisioned restrictive OS access controls. It does not require or imply Windows Protected Process Light. Verify process owner, DACL and denied handle/query rights from the attacker profile; a passing pipe PID check or a masked field establishes only its own observation. The threat model assumes the supported OS/security configuration prevents the participant from copying the native UI or tampering with the trusted binaries. Failed mitigations or missing test visibility block the pilot. Follow [C10](test-plan.md#leakage-coverage) for exact value and evidence boundaries.
