# Feasibility and design decisions

| Topic | Documented or independently observed baseline | Still to prove on the packaged ARM64 pilot |
| --- | --- | --- |
| Desktop bridge | COU-6 records Desktop 0.1.16 / hc 0.1.21 with an isolated profile. A fixture mod opened and launched a separate process with an inert ID. The observed process completed with typed stdout and empty stderr. The installed helper separately showed a native masked control and a current-user DPAPI in-memory round trip. The static mod check did not await that action's completion. The SDK is an execution and capture surface. [Pinned SDK](https://github.com/herdrdev/herdr-app/blob/v0.1.16/defaults/herdr.d.ts) | Fixed installed activation path, scrubbed environment for the next child, no grant from Desktop, two complete flows through a live managed run, and an actual local ARM64 package. Masking proves neither consent nor protected reveal. |
| Run identity | COU-6 separately observed two same-user fixture peers connecting to a local pipe and Windows returning the actual client PID. A fixture filter accepted the expected process and denied the other. Windows provides pipe access control and process handles independent of reusable process IDs. [Pipe ACLs](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights) · [Pipe client PID](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeclientprocessid) · [Process handles and identifiers](https://learn.microsoft.com/en-us/windows/win32/procthread/process-handles-and-identifiers) | Protected Herdr-to-supervisor lifecycle handshake, actual pinned process, token, creation time, rights, channel peer verification and replacement, including real OS negative controls. |
| Local pipe security QoS | Windows lets a local client cap impersonation at identification and lets the server query the effective thread token after reading a message. The earlier Plane fixture checked peer PID. [Client flags](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) · [Effective levels](https://learn.microsoft.com/en-us/windows/win32/secauthz/impersonation-levels) | The installed receiver's effective-level check on each channel and fresh connection, rejection of excess or unverifiable authority and identity-only handling on outbound broker clients. |
| Native trust | Windows has separate user sessions and desktop access controls. Window display affinity protects against some public capture surfaces and has documented limitations. [Fast user switching](https://learn.microsoft.com/en-us/windows/win32/shell/fastuserswitching) · [Desktop ACLs](https://learn.microsoft.com/en-us/windows/win32/winstation/desktop-security-and-access-rights) · [Capture affinity](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowdisplayaffinity) | Native UI integrity, active console/session checks, user verification and switching, keyboard/focus/metadata accessibility, isolation against the ordinary participant and sanitized evidence. |
| Local custody | DPAPI current-user protection is tied to the credential context and usually to the computer. The matrix reports only an in-memory trial under its test account. [DPAPI protection](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata) | Pinned broker identity, loaded profile, restrictive custody and recovery files on local NTFS, encrypted staging and crash-path inspections. Same user alone does not isolate processes. |
| Durability and time | SQLite documents WAL and a sync at every write commit in FULL mode. Windows interrupt time is distinct from adjustable wall time. [SQLite WAL](https://www.sqlite.org/wal.html) · [SQLite synchronization](https://www.sqlite.org/pragma.html#pragma_synchronous) · [Windows interrupt time](https://learn.microsoft.com/en-us/windows/win32/api/realtimeapiset/nf-realtimeapiset-queryinterrupttime) | The chosen native VFS and actual volume, ordinary process termination and restart, persistence barriers and no replay. Report storage/hardware assumptions. An OS power-cut claim needs separately executed evidence. |

Choose a separate operator Windows account and local interactive session for the first pilot. This makes consent independent of the participant's desktop and creates a concrete verification step through Windows sign-in. The isolated account, approved package and operator ceremony are explicit deployment conditions.

Use a broker-verified native enrollment anchored to a managed launch and process handle. The local named pipe serves as the authenticated channel so the pilot need not depend on handle inheritance across Windows sessions. The holder's process integrity and peer identity are required together.

Use a single broker writer with SQLite WAL/FULL on local NTFS and current-user DPAPI bound to the broker for retained ciphertext. Preserve unsuccessful and unknown attempts. The external effect cannot join the local transaction. The fake's independently retained metadata receipt can resolve an uncertain dispatch when it exists.

None of these documentation findings or Plane's feasibility probes exercised the two complete protected flows. The design treats each gap above as a gate and disables the pilot on failure.
