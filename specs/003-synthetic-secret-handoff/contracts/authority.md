# Native authority and enrollment

## Authority domains

| Caller | Accepted authority | Commands |
| --- | --- | --- |
| Herdr Workspace or ordinary CLI/MCP | Read-only projection in verified local project scope, and a non-authorizing candidate reference | List, inspect, request opening the installed bridge. |
| Trusted local launch supervisor | Pinned native peer, protected profile and run handshake | Publish a live managed run, attach the exact participant process, replace or end an enrolled generation. |
| Enrolled participant | Broker-pinned live process and token in that generation, local IPC verified per connection | Request A, explicitly offer B, cancel own pending contribution, invoke the approved A operation, read its receipts. |
| Operator | Dedicated Windows logon SID and active local console, approved native UI process and current broker UI channel | Create A offer or B request, approve A, accept B, deny, cancel own pending request, revoke, show B once, request reconciliation. |
| Broker and fake | Restricted service principals on authenticated private channels | Broker fences, encrypts and invokes. Fake executes one fixed operation and supplies typed receipt evidence. |

Workspace, participant and operator are never credited as one another. User-configurable metadata, roles, repo strings, dates, OS PID, terminal address and request IDs are display/correlation inputs only. Formal Council approval and saved work item state have no broker rights.

## Pinned pilot setup

Administrator provisioning enrolls the signed/hash-pinned ARM64 native package and identities into an ACL-protected system directory. Use distinct service/launch-supervisor, fixture participant and dedicated operator identities. The protected manifest includes stable pilot project ID plus an already-resolved local volume and directory identity, eligible managed role ID, fixed adapter and route versions, SID mappings and the deadline policy. The operator native process and the broker/fake services run from installed absolute paths with protected library search, a safe working directory and an allowlisted environment. Reject path aliases that fail physical identity verification, another checkout, replacement binaries, and writable/reparse install roots. No project file or inherited environment can change this registry.

Keep core terminal launch and lifetime under Herdr. Only a setup in which the pinned launch supervisor can attest to a genuinely managed run with a protected control channel is eligible. The isolated pilot core/launcher control endpoint and protected launch-intent state are inaccessible to the participant. A trusted supervisor issues a run intent against the installed project, role, reserved Council session ID and saved run deadline, and associates it once with Herdr's actual successful owned launch and authorized process. Accept creation and delivery evidence from the trusted launch path plus process liveness. The weak inputs (session file, terminal address, environment hints and editable role configuration) cannot enroll independently. Eligible launch cannot adopt a terminal, attach authority to an existing unrelated process, or accept arbitrary shell/command/image configuration. If a supported Herdr-managed path cannot produce this handshake the pilot remains unavailable. A supervised native adapter entry point may be added after the spec gate. An independent harness process next to a terminal does not satisfy the live enrollment gate.

## Local pipe impersonation boundary

Every pilot pipe client opens only the installed local endpoint with `CreateFileW` and `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION` explicitly in `dwFlagsAndAttributes`. Use static security context tracking and a non-inheritable handle. Every pilot listener rejects remote clients and uses its explicit local ACL. The pilot requires verified identity on every endpoint, so an anonymous client cannot use these endpoints. Reject an unavailable explicit-QoS open. Do not fall back to a default open, a runtime wrapper that cannot set these flags, or a remote endpoint. The client still verifies the pinned server process and installation before sending its preface. [Client open flags](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) · [Named pipe impersonation](https://learn.microsoft.com/en-us/windows/win32/ipc/impersonating-a-named-pipe-client)

| Pipe client → listener | Covered use |
| --- | --- |
| Workspace bridge or local metadata reader → broker | Reference staging and scoped metadata lookup. |
| Trusted managed-launch peer → launch supervisor, and supervisor → broker | Protected live launch, run lease, replacement and end. |
| Enrolled participant → broker | Participant requests, offers, invocation and receipts. |
| Installed operator UI → broker | Consent, decisions and protected action requests. |
| Broker → native renderer | Dedicated one-shot replay-protected render channel and acknowledgement. |
| Broker → fixed fake | Fixed dispatch and read-only reconciliation. |

Each row names the OS client and listener. Replies on a duplex pipe share that open. A separate connection in either direction must run the same opener and receiver checks. If a launch integration uses another privileged pipe hop, it is covered by the same rule and test before it can carry authority.

On each connection the server reads a bounded, value-free preface. Bind the Windows token check to the last frame read on that exact pipe instance. Serialize reading and checking per instance. On a dedicated native thread, call `ImpersonateNamedPipeClient`, open the thread token with `OpenThreadToken(TOKEN_QUERY, OpenAsSelf = TRUE)`, then use `GetTokenInformation` to require `TokenType == TokenImpersonation` and effective `TokenImpersonationLevel == SecurityIdentification`. Check the minimal token identity fields against the OS-pinned peer (user and logon SID and session). Use the same receive gate on every client command or effect frame before acting. Revert on all paths after successful impersonation, dispose the query handle and identity buffers locally, and complete only after successful `RevertToSelf`. Never duplicate, delegate, persist or transmit an access token, its handle or raw token fields. No dispatch, storage, DPAPI, logging or application callback runs under a client token. An anonymous, overprivileged, unreadable or mismatched token, or a failed API call, rejects the connection. A failed revert stops the serving process and invokes the normal restart rules. The pinned server sends a typed ready response only after the preface passes and the thread has reverted. Wait for readiness before sending authority commands or any canary. [OpenThreadToken](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-openthreadtoken) · [Effective token level](https://learn.microsoft.com/en-us/windows/win32/secauthz/impersonation-levels) · [RevertToSelf](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-reverttoself)

A small native test observer reads the result of the same server-side checks on the installed data path for every channel role, including outbound broker clients. Report only channel/direction, step disposition, level category and assertion counts. Test the open and handshake afresh on reconnect. Probe unavailable query and default/overbroad opens in separate synthetic negative runs, with zero privileged actions. A configured flag, pipe ACL, PID check or application-provided claim alone cannot establish effective impersonation level. See [native SQOS checks](../test-plan.md#native-pipe-sqos-checks).

## Peer and lifetime checks

The supervisor starts the fixed native participant fixture with the participant token and trusted-owner restrictive process/thread descriptors before allowing execution. The broker retains an OS handle to the actual created process and records creation time, token user SID, unique logon SID and Windows session ID. Dedicated service principals control handle creation and transfer through their restricted channels. On every authority IPC connection, use explicit local pipe ACL and local-only mode, authenticate the token/logon and verify OS-reported peer PID, creation time and identity against that same live process object. The client verifies the expected live server process and installed binary identity before use. Use equivalent kernel-backed checks for supervisor, native UI and fake server. Reject process exit, double registration, ambiguous startup, endpoint collision and failed identity queries. Do not grant unrelated processes the ability to duplicate handles, write/inject, create threads, take ownership or change ACLs on enrolled process objects. Use no inherited ambient authority. PID rollover and a same user peer with a copied ID confer no authority. No enrollment token is delivered through shell, terminal, env, argv, a mutable file or MCP.

Bind the lease to `projectId`, `runId`, stable managed `roleId`, `participantPrincipalId`, `recipientGeneration`, `brokerEpoch`, and `runDeadlineUtc`. Generation is allocated by the broker and changes on enrolled process replacement, reassignment, role change, or new launch attempt under the same run. Process death, run completion, cancellation, deadline, authenticated supervisor disconnect/loss of freshness, or restart prevents further authorization. Keep a live supervisor guard and check it, the process handle and current generation at claim and at the irreversible fence. The supervisor serializes managed lifecycle publications with the broker and acknowledges invalidation before exposing a deliberate replacement. If process death or an unplanned host event occurs after the irreversible fence, preserve the known result or uncertainty for that attempt. Re-enrollment never transfers old consent.

Expose verified identity to the UI through immutable broker records. Use a provisioned identity label plus stable role/principal ID, run ID and generation. Sanitize or omit any reported names and use separate visual treatment for optional descriptive labels. The approval record must identify the exact attached participant instance even when the human is the reveal recipient. [Threat model](../threat-model.md) · [Native UI](operator-ui.md).
