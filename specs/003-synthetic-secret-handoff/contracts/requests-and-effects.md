# Requests, durable effects and recovery

## Input and projection

Use version 1 typed, length-bounded local messages. Reject unknown fields, unsupported schema/opcode, duplicate JSON keys and malformed IDs before mutation. Derive actor from the authenticated channel. Use broker-generated request and operation IDs. Opening mutations accept a 128-bit opaque client idempotency key and typed direction/intent and target stable IDs. A matching key and normalized tuple under the same verified initiating principal returns the original projection. The same key with changed input returns `conflict`; another principal cannot use it. Server receipts and audit never echo unrecognized input, bytes or raw exception text. Keep purpose, its display label, operation, adapter version, destination and named output from the fixed catalog.

A request has one immutable revision for the pilot. An edit creates a new request ID. Persist the exact tuple `[version, requestId, revision, projectId, runId, roleId, recipientGeneration, initiatorId, participantPrincipalId, recipientPrincipalId, direction, purposeId, operationIdFromCatalog, adapterVersion, destinationId, requestExpiresUtc]`. Consent additionally binds `approverPrincipalId`, the operator logon lease, effective `expiresUtc`, and `maxUses = 1`. Display these terms before commitment. Decision, use and reveal commands echo request ID and revision. Consent and reveal gestures use server-issued single-use, action-specific prompt context in the authenticated UI channel. Launch/lookup has no prompt capability. Recheck live grant, sender, recipient and tuple at both claim and start.

Project view may include schema version, request ID and revision, project/run/role/generation, verified IDs and fixed labels appropriate to the caller, direction, timestamps, status, typed category, next action, and receipt ID. A consumption reply may include only `version`, `outcome` and `receiptId` (null when no receipt). Use fixed outcomes such as `succeeded`, `already_handled`, `not_authorized`, `expired`, `unavailable` and `delivery_uncertain`. Error messages are local strings keyed by typed code. No receipt contains a canary, derived secret, raw response body, path or trace.

## Lifecycle and deadlines

| Start | Authorized sequence |
| --- | --- |
| A operator offer | Operator creates an offer targeting the live participant. Operator **Approves use** in native UI and selects a broker-generated synthetic entry. Enrolled participant invokes, accepting and consuming through the verified run. |
| A participant request | Verified participant opens the request. Operator **Approves use** and selects the synthetic entry. The same verified participant invokes once. |
| B participant offer | Verified participant explicitly offers the named output to the designated operator. Registered adapter generates a distinct synthetic output within broker custody. Operator **Accepts offer**, then separately chooses **Show once**. |
| B operator request | Operator requests the named output. Verified participant separately offers it to that operator. Generation, acceptance and Show follow the same rules as the B offer. |

Sequences attribute each human, participant and broker event independently. B offer and staging commit together or fail closed. B staging generates inside the broker via the same fixed adapter and is reversible custody, with no independent external dispatch. No irreversible effect before the ordered decision and use/show. A pending version can be denied by the designated operator, or cancelled by the initiating actor before approval. During a B offer responding to an operator request, the enrolled offering actor may also withdraw the offer before acceptance. Terminal denied/cancelled versions reject later approval. For approved requests use revoke. Closing has no state effect.

Set pending deadline to the earlier of run deadline and configured pending lifetime, capped at 15 minutes from creation. Effective consent expiry is the earliest of the request expiry, saved run deadline, approval instant plus operator-selected duration, and approval plus 15 minutes. Default duration is five minutes. Durations are positive whole seconds. UTC comparison is strict (now < expiry) with a monotonic deadline derived at approval and elapsed through sleep. Retain the last observed UTC high-water mark within the broker epoch. A backwards sample or unavailable trustworthy clock invalidates outstanding rights. The monotonic bound is independent, so UTC drift or a missed rollback cannot extend the elapsed duration. Persist absolute expiry and approval time. On every broker start, invalidate preexisting unused approvals and pending requests before accepting commands, retain the original UTC values, classify already elapsed records as expired, and require a fresh enrolled generation, request and native consent for future effects.

## Commit boundary

Use one local broker writer, SQLite WAL with synchronous FULL on a provisioned local NTFS volume, and durable uniqueness for the request idempotency key and one effect per request revision. All connections honor the selected durability mode. The broker writes state, append-only metadata event and receipt indexes in the same transaction. No process sends or renders on a failed or ambiguous commit. Operations follow this ordering:

1. **Claim** atomically checks request, grant, actor, run, deadline and one-use constraint, allocates the durable effect ID and records `claimed`. No I/O that might use or reveal the value has occurred. A lost claimant can only be fenced off. No replacement claimant continues it.
2. **Start** checks all authority and deadline again under the same serialization as revoke and lifecycle invalidation. Commit `effect_started` with effect ID and exact route or renderer lease, then allow the live claim owner to attempt the external effect once. The successful durable Start commit is the point of no return for the policy. No automatically retried network write, redirection, frame resend or UI retry. Establish local peer trust and prepare safely in advance where possible. If a precondition is lost after Start and the broker can prove it never called the transport/render operation, it may durably store a terminal no-effect receipt. Otherwise retain uncertainty.
3. **Execute** A with a single bounded send to the pinned fake service, or B with one authenticated frame delivered to the current verified native renderer. The renderer deduplicates by effect ID in its live instance and never persists a value or displays a second frame for that ID. Clear native value bytes as soon as used. Broker stores the authenticated fake receipt or explicit render acknowledgement durably before reporting success. A render acknowledgement proves the specific control displayed once, and carries no value.
4. **Revoke** serializes at the same boundary. Before Start it fences claim and records revocation, with no dispatch or reveal. After Start it records a late revoke, prohibits future uses and preserves or resolves the attempt. The irreversible attempt may still finish once even when local revoke cannot recall it. Decline, expiry and run invalidation use the corresponding pre-start fence rules. Active-session loss additionally forces the native renderer to clear or decline paint. Release staged ciphertext no longer needed after fencing. Any already-started render may use the value already handed to its live claim only within that render lease.

The A adapter connects only to a broker-provisioned local, mutually verified private endpoint. No arbitrary address, proxy, URI, network fallback or route following. The fake internally verifies the canary and commits its independently durable typed receipt with the synthetic effect in its own store. An unexpected redirect-like response is an error and never triggers a second endpoint connection. The broker and fake wipe memory buffers after bounded use. A separate read-only fake receipt lookup by effect ID cannot invoke the operation.

## Restart and reconciliation

On startup serialize recovery before availability. Corrupt or unreadable state disables the protected action. Keep history and actor attribution. A claim without Start can be proven to have no external effect and is terminally invalidated after restart. A Start without a durably committed receipt is `delivery_uncertain` regardless of local caller timeout or lack of apparent output. Compare the original A effect ID to the fake's independently durable authenticated matching receipt. A positive match can resolve, and missing or contradictory evidence remains uncertain. B has no independently durable external reveal proof for a lost acknowledgement; retain uncertainty and never reveal again for the old request. B control acknowledgement already committed in broker storage is a known receipt and lookup is metadata-only. Retrying reads, re-enrolling, an app retry or a machine restart always preserve the old attempt and ID. No transport retries are triggered by reconciliation. New consent for a distinct request is deliberate and separate from the previous unresolved delivery.

Retained synthetic ciphertext uses current-user DPAPI under the dedicated broker profile in the protected store (no machine-scope fallback). Audit fields and observation counts use safe schemas. Details in the [data model](../data-model.md) and [leakage gate](../test-plan.md#leakage-coverage).
