# Durable data model

| Record | Bound fields |
| --- | --- |
| Scope/profile | Installation UUID, enrolled canonical local project, Plane instance UUID and normalized exact origin, workspace slug/UUID, project key/UUID, expected integration principal UUID, public GitHub registry with exact slug and numeric repository ID. A changed pin disables that profile until re-enrolled. |
| Link | Local item ID, private canonical scope key, link revision (initially 1), profile pins, Plane item UUID and sequence, confirmation ID, operator principal reference and time. The immutable link key covers both sides. |
| Preview | Random 128-bit lowercase hex operation ID, unique snapshot key, item/lifecycle revision, link revision, target identity, restricted status and URL, expected API author, `INTERNAL`, serialized payload digest, created and expires time, protocol version. |
| Approval | Original preview digest and operation ID, operator principal reference and time. Approval expires with the preview. The publisher records decisions in its own state after authenticated operator action. |
| Start | Original operation ID, immutable approval and pins, publisher/fence schema version and timestamp. Durable exclusive event publication grants only the winning live call the authority to send. |
| Receipt | Original operation, Sealed target identity and author, canonical comment UUID, normalized comment digest, at and source (`response\|reconciliation`). Retain receipt by operation across focus changes and restart. The durable commit of an equivalent receipt in a recovery race is idempotent. Record a conflicting proof attempt without replacing a positively verified receipt. |

Calculate the snapshot key from a versioned canonical tuple of scope, item ID, link revision, lifecycle revision, status and evidence URL. Repeated intent for the same key returns the current operation or the existing receipt. Supersession requires explicit operator action, an unstarted expired/cancelled/stale preview and a new operation ID. Record supersession by ID. Never release a started slot for missing evidence. An independently newer local revision can form a new snapshot after positive reconciliation. No other event resolves Start in this release.

## Journal and durability

Register the physical project via an operator profile. Validate realpath, installation identity and item ID from that profile and recompute the current COU-8 projection through a trusted installed reader. Resolve no path from a renderer-provided ref. Reject unknown, redirected, replaced or unsupported roots. The publisher owns its private journal, installation identity, locks, outbox and credential reference. Do not store these under worker-writable project output. Root validation, owner-only ACL, exclusive append, no-clobber publication, file flush before publish, proven directory/metadata durability before send, and restart recovery are deployment requirements. A platform on which these primitives are unproven disables the sender. Validate a revisioned hash chain, bounded records and the same physical file identities when reopening; surface any corrupt tail as blocked and preserve the readable prefix. A transient write error never grants send authority. Use an exclusively published record, not a revivable lock or lease; do not send after recovering an existing Start. Recovery may compete to record a receipt but cannot remove or replace authorization. An unreadable or insecure journal remains blocked. If Start's publication acknowledgement is lost, reopen for read-only recovery.

An operation transitions `prepared → approved_unsent → delivery_uncertain → published`. The durable Start record makes the operation uncertain until validated receipt commits. Before Start `expired`, `cancelled`, `conflict` or `offline` may be exposed with no network side effect; an approved record carries no permission to dispatch after process exit. New Start requires a fresh trusted confirmation in the same live request while still bound to current state and verification. The winning process may make one call. Parallel local writes after the fresh revision read can make the published snapshot historical; they cannot change its exact bytes. Record the historical revision and show when a newer Council revision exists.

Expose a metadata-only projection to the Workspace/ordinary CLI/MCP from the private owner through a bounded read interface, or through a replace-atomically exported operator-owned read projection verified against installation and scope. An unavailable or stale projection carries its freshness and cannot authorize an action or imply that a pending operation is complete. Worker principals cannot modify the operator state, installed publisher or accepted projection. Terms such as disabled, uncertain and receipt have the same meaning across surfaces.
