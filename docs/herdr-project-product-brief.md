The vault has its own gate. An individual work item can wait for a secret while the rest of the project remains usable offline.

**Work item integrity.** Keep item lifecycle, execution attempts, and review verdicts independently visible. Persist the item revision and run ID before dispatch and check that link on retry. If the criteria change, show the revision the agent received and let the lead decide whether to accept or rerun. Transport receipts, Git changes and advisory votes cannot authorize acceptance. Formal authorization still requires direct valid ballots from completed participants, tied to the exact proposal digest. Provisional reports stay under `validation/`. Approved reports move to `reports/` after the existing checks pass. In Workspace, start at the project queue and open an item to see its criteria, responsible role, blockers, linked attempts, evidence, and next action. Each attempt links to its saved Council result and live terminal when present. The lead sees ready, active, blocked, awaiting review, and closed work with an action appropriate to each state. Keep the same record IDs through app restart and worktree navigation. Test two adjacent checkouts with identical item titles and verify that every write stays in its selected project scope.

## Secret handoff design

### Consent and delivery

Workspace exposes request metadata and opens a trusted native broker with a non-authorizing request ID. The native prompt shows the verified project, run, requester, recipient, operation and destination. Validate the handoff on the installed SDK with synthetic input first. Disable the action wherever a trusted prompt or runtime binding is unavailable. [Herdr mod SDK](https://github.com/herdrdev/herdr-app/blob/master/defaults/AGENTS.md)

| Direction | Request and consent | Delivery |
| --- | --- | --- |
| Human → agent operation | A human can offer access, or an enrolled agent can request a named operation. In the broker UI the human chooses a stored entry or supplies one through secure native input, then approves the exact recipient, destination and duration. The recipient accepts by invoking the approved operation. | Bind the grant to the project, run, launch identity and generation, and fixed adapter. The broker uses the value on the approved route and returns a typed result or receipt. The agent can use the capability without receiving the value. |
| Agent operation → human | The human can request a credential produced by a registered operation, or an enrolled agent can offer one. An authorized adapter supplies it directly to the broker. The agent explicitly offers the named output and the authenticated human explicitly accepts before access. | Deliver once via protected native reveal, or save to that human's OS vault by explicit choice. If a credential entered the conversation or terminal output, generate a fresh credential through the registered adapter. |

Bind approval to the request version, actor, recipient principal, project, run, direction, allowlisted adapter/destination and absolute expiry. Default to one use within five minutes, with expiry capped by the job deadline and a 15-minute maximum. Changes to recipient, purpose, destination, or duration require fresh consent. Decline, expiry, run end, revocation and recipient replacement invalidate outstanding grants. Serialize revocation and the one-use claim. Lost acknowledgement after dispatch yields an explicit uncertain state and blocks replay. Surface a provider revocation or rotation action when available. Local revocation blocks future use. A manually copied value or already dispatched operation is outside local recall. Audit only stable IDs, actors, operation ID, timestamps, delivery state and failure category.

### Local storage and process boundaries

| Platform | Proposed storage and channel |
| --- | --- |
| Windows | Use current-user DPAPI and a broker-private ACL on the encrypted store. Restrict the local named pipe to the intended user/logon SID, reject remote clients and authenticate the enrolled client session in addition to the OS identity. Validate the x64 and Ejupi Labs Arm64 packages independently. [DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata) · [Named pipe security](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights) |
| macOS | Use Keychain Services with access constrained to the signed broker. Use a Unix-domain connection in a private runtime directory and check the peer credentials together with broker enrollment. Fail closed on denied or locked Keychain access. [Keychain access control](https://developer.apple.com/documentation/security/access-control-lists) · [Peer credentials](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man3/getpeereid.3.html) |
| Linux | Use Secret Service on the user's D-Bus session with locked collections and supported native prompts. Put a Unix-domain socket in the user's private runtime directory and check peer credentials and enrollment. A missing or locked service leaves access unavailable until a supported store is unlocked. [Secret Service](https://specifications.freedesktop.org/secret-service/latest/) · [XDG runtime directory](https://specifications.freedesktop.org/basedir/latest/) · [Linux UNIX sockets](https://man7.org/linux/man-pages/man7/unix.7.html) |

OS identity and a terminal address cannot establish which agent turn owns a grant. Enroll a broker-launched helper through an inherited private handle or equivalent authenticated channel, bind it to the run generation, and use broker-controlled fixed adapter operations. Test the boundary with a second process under the same user. An unenrolled terminal can request help through metadata. Receipt, tool result and request ID confer no authority. The local guarantee assumes a trusted host and excludes administrator access and debugging of broker memory.

The value stays in the approved native store, broker memory and fixed operation, or a deliberate native reveal. The broker constructs the operation to the approved destination and rejects unapproved redirects. Keep values out of model input/output, MCP, chats, tickets, the PTY and capture, stdout/stderr, audit logs, dumps, telemetry, process arguments, inherited environments, workspace files and Git. Disable plaintext persistence and clipboard export. Release only typed result fields with no raw response body. Keep cleartext lifetime short and disable broker crash capture of secret-bearing memory where supported. Any platform that cannot meet the boundary stays disabled.

### Vault release gate

Generate random synthetic canaries inside the fixture broker, with a controlled fake service. Record only check outcomes and request IDs. On each enabled OS verify both directions, denial, cancellation, a wrong user/project/run/recipient, an unenrolled process under the same user, recipient replacement, expiry, revoke racing with delivery, concurrent duplicate consumption, lost acknowledgement, unavailable or locked storage, forced exit and restart. Require one delivery per accepted one-use grant, zero deliveries for invalid or refused requests and zero automatic replays after uncertain dispatch. Assert zero canary occurrences in chat, Plane payloads, PTY and captured artifacts, logs, telemetry, process arguments, environment and Git including staged files. Require a real native UI and broker test on each enabled OS and an independent review of the storage, process boundary and revocation behavior before enabling real values.

After the separate specification is reviewed, start the pilot with one fixed operation against the fake service. An enrolled agent requests permission to invoke it for a single task. The broker uses a synthetic credential and returns success metadata to the agent. The same adapter can produce a distinct synthetic output for an explicit offer, then the human accepts and reveals it in the native UI. Record evidence before replacing the fake route with a provider.
